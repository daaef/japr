# Problem: No way for editors to send targeted nudges to other roles

## Symptoms

1. **Editors cannot ping individual users about specific manuscripts.** When a managing editor
   needs to remind a reviewer about a pending review, or alert the EIC that a new manuscript
   needs attention, they have no in-app mechanism to do so. They must reach out via email or
   another channel outside the system.

2. **The only automated reminder is the cron-based reviewer deadline reminder**
   (`server/utils/reviewerReminders.ts`). This fires once, 48 hours before the deadline, and
   cannot be triggered manually. There is no equivalent for any other role or situation.

3. **There is no preset message system.** Every notification in the system is generated by a
   workflow event (submission, assignment, review completion, etc.). There's no concept of a
   user-initiated message — "ping the managing editor that a new manuscript arrived" or "remind
   the author their revision is overdue."

## What the team wants

- **Desk editors** (and other editor roles) should be able to send preset messages to specific
  roles or users, tied to a manuscript context. Examples:
  - Ping managing editor: "New manuscript received — please review for reviewer assignment."
  - Ping associate editor: "Your review deadline is approaching."
  - Ping author: "Your revision is overdue."
  - Ping EIC: "All reviews are in — final decision needed."
  - Ping admin: "Need help with [manuscript title]."

- The ability to ping should itself be a configurable permission (from the
  configurable-permissions task).

- Preset messages should be role-aware: the available templates change based on the target
  role and the manuscript's current status.

## Current infrastructure to build on

- **Notification model** (`server/db/schema/notifications.ts`): `{ userId, type, data (jsonb),
  readAt, createdAt }`. The `data` blob conventionally holds `title`, `message`, `action_url`,
  `journalId`, `icon`, `color`, `priority`. No schema changes needed for basic ping delivery.

- **`createNotification` / `createNotifications`** (`server/utils/notifications.ts`): Insert +
  SSE realtime publish. Already supports bulk sends.

- **Email** (`server/utils/email.ts`): `sendEmail` + `sendIfEmailAllowed` with preference
  gating. 20+ typed senders exist as precedent.

- **Notification preferences** (`server/utils/notificationPreferences.ts`): Three email
  categories: `manuscript_status`, `review_assignment`, `new_submissions`. A ping system would
  need either a new category or reuse of an existing one.

- **Reviewer reminders** (`server/utils/reviewerReminders.ts`): The closest existing pattern —
  finds users to nudge, deduplicates via `remindedAt`, sends notification + email. Manual pings
  would not use the cron pattern but would reuse the send shape.

- **No alert banner system exists.** The user mentioned "alert banners" — today these are ad-hoc
  `<UAlert>` components per page, not a centralized notification-banner mechanism. A ping
  delivered as a high-priority in-app notification (which already shows a badge + optional
  desktop notification) may be sufficient without building a separate banner system.

## Scope

Design a ping/nudge feature:
1. Data model for ping templates (preset messages per target role + manuscript status).
2. API endpoint(s) for sending a ping.
3. Permission model (who can ping whom).
4. Delivery: in-app notification + email (reusing existing infrastructure).
5. Deduplication: prevent spam (cooldown or rate limit per sender/target/manuscript).
6. UI: a "Ping" button or menu on the editor manuscript detail page.
